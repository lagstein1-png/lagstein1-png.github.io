## 1. מה נבנה

**מוח אחד לכל האפליקציות.** השרת (`tutor-api/worker.js`) מקבל עכשיו

אם היא הצליחה מוצג המשפט שמלווה אותה. נכשלה — ברק אומר ״לא הצלחתי
לעשות את זה עכשיו״ במקום להעמיד פנים. זה סוגר את ״נעבור למסך״ שלא
מעביר.

8 שניות בלי תשובה, נגמרה המכסה, השרת נפל) עובר בשקט למוח המקומי
שבמכשיר, שגם הוא יודע לבצע ״הבא״, ״רמז״ ו״תקריא״ בארבע השפות.

## 4. מה לנסות בטלפון — חמש בדיקות

**חמש הבדיקות האלה דורשות את המיזוג, וזה תוקן כאן 16.9.2026.**

החדש אינו על הטלפון עד שהמיזוג נעשה. מה שאפשר לבדוק לפני כן הוא
הסטייג׳ינג (5א), והוא בודק את **השרת** ולא את המסך.

הסדר המעשי: 5א (סטייג׳ינג) ← `barak-live` ← ״יאללה״ ← 5ב צעד 1
(השרת) ← 5ב צעד 2 (האתר) ← וכאן חמש הבדיקות.

1. **ברק רואה את המסך.** פתח `math-app`, ענה תשובה שגויה, לחץ ״ברק —
   עזרה מהמורה״ וכתוב ״למה טעיתי?״. הוא צריך להתייחס למספר שבחרת,
   בלי לומר את התשובה הנכונה.
2. **״נעבור לשאלה הבאה״ באמת עובר.** באותו פאנל כתוב ״תעביר אותי

3. **רמז שלא מגלה.** בשאלה חדשה כתוב ״רמז״. הרמז נפתח על המסך

4. **מצב טיסה.** כבה את הרשת, כתוב ״הבא״ ואז ״לא הבנתי״. השאלה
   מתחלפת, ברק עונה מהמכשיר עם שורה קטנה ״התשובה מהמכשיר, לא

5. **ארבע שפות.** החלף את שפת האפליקציה לערבית / רוסית / אנגלית

## 5. פקודת ה״יאללה״

### א. סטייג׳ינג (מותר עכשיו, אינו נוגע בייצור)

GitHub → Actions → **deploy-tutor-staging** → Run workflow → הקלד
`STAGING`. הוורקפלו יוצר `tutor-staging`, מעלה את `GEMINI_API_KEY`
שכבר ב-Secrets, ומדפיס בסיכום את `/health` ו-`/ask`. ואז, לבדיקת
המודל האמיתי: Actions → **barak-live** → Run workflow.

### ב. הייצור — השרת קודם, ואז האתר

**הסדר הזה תוקן 16.9.2026, והוא הפוך ממה שנכתב כאן קודם.** הנימוק
נמדד בקוד, ולא בהיגיון של ״קודם ממזגים״:

- **השרת החדש מבין גם לקוח ישן.** `readBody` מקבל את הגוף הישן
  (`q`, `messages`) בדיוק כמו את החדש, ו-`/` נשאר נתיב חוקי. כלומר
  פריסה של השרת לפני המיזוג אינה שוברת אף לומד שמחזיק היום את
  האתר הישן.
- **הלקוח החדש מול שרת ישן — מאבד את ברק.** הוא שולח `screen`
  ו-`userText`, השרת הישן מחזיר 400, והלקוח נופל למוח המקומי
  **בלי שגיאה**. הלומד לא רואה תקלה, אבל גם לא מקבל את המורה
  שבשרת. זה בדיוק החלון שהסדר ההפוך יוצר.

**לכן: 1. השרת. 2. האתר.**

**צעד 1 — השרת.** GitHub → Actions → **deploy-tutor** → Run workflow →
`DEPLOY`. אפשר להריץ אותו על הענף (״Use workflow from״ →
`claude/barak-core-full-build-2gyyk4`) עוד לפני המיזוג. הבדיקה החיה
בסוף הוורקפלו חייבת להחזיר 200.

**צעד 2 — האתר.** בריפו הראשי, מטרמינל עם `git`:

    git fetch origin main claude/barak-core-full-build-2gyyk4
    git checkout main && git merge --no-ff origin/claude/barak-core-full-build-2gyyk4
    node .claude/qa/all.js --static && git push origin main

(אם `main` זז מאז והמפתחות התנגשו — `node .claude/qa/cache.js` יאמר
איזה מפתח להעלות; זה הכלל ״המספר מוקצה במיזוג״.)

ובריפו של ״תאוריה מדברת״:

    git fetch origin main claude/barak-core-full-build-2gyyk4
    git checkout main && git merge --no-ff origin/claude/barak-core-full-build-2gyyk4

### ג. איך חוזרים אחורה

- **השרת:** Actions → deploy-tutor → Run workflow על הקומיט הקודם
  של `main` (בחר ב-״Use workflow from״ את התג/הענף הישן), או
  ב-Cloudflare: Workers → tutor → Deployments → Rollback לגרסה
  הקודמת. הלקוחות הישנים ממשיכים לעבוד מול ה-Worker החדש (הגוף
  הישן מתקבל), והחדשים מול הישן (נופלים לטקסט בלי פעולות) — אין
  צירוף שבור.

  שוב את 13 המפתחות (`node .claude/qa/cache.js` מונה אותם), כי
